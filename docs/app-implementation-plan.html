Framework grounding

Every claim below was checked against current documentation rather than recalled.

  • Agents — pydantic-ai. Programmatic hand-off (req 11) is a documented pattern: agents called in succession from plain Python, each run scoped to one requirement slice, context carried by message_history and shared deps/usage. No graph DSL — the state machine is our own explicit loop.
  • Evals — pydantic-evals. Same ecosystem: Case, Dataset, Evaluator, plus built-in LLMJudge, IsInstance and MaxDuration(seconds=…) — the latency assertion, first-class. EvaluatorContext exposes ctx.duration, ctx.metrics and ctx.span_tree, so correctness, latency and token cost all fall out of one run.
  • Shared state (req 12) is a deps dataclass holding the Artifact object. Tools mutate it in place; it outlives every run.
  • Gemini. GoogleModel(<id>, provider=GoogleProvider(api_key=…)), with HttpRetryOptions for transport retry and UsageLimits per slice.
  • Comments. document.add_comment(runs=…, text=…, author=…) and document.comments exist in python-docx ≥ 1.2.
One correction worth flagging

The obvious reading of reqs 16–17 puts the retry in @agent.output_validator raising ModelRetry. That handles cheap structural fixes, but exhausting its budget raises. Req 17 needs a durable terminal outcome — a requirement marked unverified in the returned comments. So the three-attempt cap and the unverified marking live in our outer loop, not in the validator.

Architecture

Email layer

The manifest is parsed exactly once, by the editor, and the list travels back. That ordering is forced by req 7: the confirmation reply has to contain the parsed requirements, so the email service cannot send it until the parse exists.

The email service has two roles, not one

This is easy to under-plan, and the first draft of this document did exactly that — it stopped at the confirmation and never delivered anything back.

Role 1 — intake, synchronous. Receive, validate, hand off, confirm.

Role 2 — delivery, asynchronous. The job finishes minutes later in another service. Something has to put the reviewed documents in front of the client, and req 10 says that output is the product. Without this leg the system does nothing useful.

The two share only the transport — different triggers, different failure modes, different idempotency keys. That is why delivery is its own branch (B13) rather than more surface area on intake.

Triggering. The editor calls back on completion, and the email service also sweeps for jobs in flight too long. Callback alone loses jobs whenever the email service is restarting; polling alone adds latency to every job. The sweep is cheap because JobRecord already exists for D2.

The delivery email carries more than attachments: a pass/fail summary so the outcome is readable without opening anything; every requirement marked unverified, called out explicitly — this is where req 17 becomes visible to a human, since the system gave up after three attempts and the client must be told which checks were never completed; and on outright failure, a message saying so, which answers most of concern D2 almost for free.

Attachment size is a constraint, not a detail

The fleet fixture's single reviewed document is 2.8 MB with 17 embedded photos. A request carrying several forms clears typical limits fast — Gmail refuses at 25 MB, many corporate servers at 10. Delivery attaches below a configured threshold and otherwise sends a signed link to the object in the bucket. The documents already live in GCS as BlobRefs, so the link costs nothing extra.

Threading sets In-Reply-To against the original client message, not the confirmation, so request → confirmation → results reads as one conversation. Idempotency is keyed on job_id: a callback that fires twice, or a callback plus the sweep catching the same job, must not send two copies.

Why not parse in both services

The tempting alternative — the email service parses for the reply, the editor parses again for the run — is a silent correctness bug. The parser has a model in it, so it is not deterministic: two parses of the same manifest can return different requirement sets. The client would be shown one list while the document is graded against another, destroying the exact thing req 7 exists to provide.

Parse once, return it in the 202, store it, never re-derive. It also keeps every model credential inside one service — the email layer never talks to Gemini.

Orchestration layer

The email-service is not only a mail gateway — it is the orchestrator. It owns the job, plans the slices, fans them out to editor instances running in parallel, collects and validates what comes back, and applies the results to one document.

Why the writes are serialised

Every editor instance receives a read-only snapshot of the artifact plus its own slice, and returns a SliceReport of proposed edits and comments. No instance writes to the document, or to the store.

That removes the hard problem rather than solving it. The alternative — N agents mutating one artifact under optimistic concurrency — produces version conflicts under exactly the load the parallelism was introduced to handle, and a retry storm where each loser re-runs a model call that already cost money.

Two properties worth more than the contention they avoid

The output is deterministic in application order. Proposals are applied in slice order, never completion order. Whichever instance finishes first, the document is byte-identical. Apply on arrival and it quietly changes between runs on the same input — which would make the golden fixture meaningless.

Conflicts become visible. The applier holds every proposal before writing anything, so two slices targeting the same line_id is a detectable event rather than a silent last-write-wins.

That second point is a real gain against concern D3. Contradictory requirements were previously invisible by construction — each agent saw only its own slice and nothing compared them. Fan-in gives the one moment where all proposals coexist, which is the only place a cross-slice contradiction can be caught. It does not solve D3 — two requirements can contradict in meaning while touching different lines — but it converts the line-level case from undetectable to detectable.

Req 12 still holds: each run gets a live Artifact it may mutate freely at any point. It is a snapshot, and the orchestrator merges the resulting edit list.

The editor becomes a worker

editor-service no longer owns a state machine or a loop. It exposes essentially one operation:

POST /slices:run    SliceRequest → SliceReport

Stateless, horizontally scalable, testable with no job lifecycle around it. The lifecycle — retries, the three-attempt cap, the unverified terminal, apply, render, deliver — belongs to the orchestrator, which is where JobRecord already lives.

Tools are scoped per instance. A slice runner is handed a toolset bounded to its own requirements and the regions they govern. A proposal targeting a line outside that scope is rejected by the applier deterministically — slice isolation is enforced by the tool layer and the applier, never by asking the prompt nicely.

Concurrency is bounded. A semaphore caps simultaneous slices and UsageLimits caps each one. Unbounded fan-out on a 40-requirement manifest is how you discover your rate limit in production.

On the name: a service doing mail I/O and orchestration is doing two jobs and the name mentions one. Internally it splits orchestrator/ from mail/ — transport as adapter, orchestration as core — so the seam is there the day it wants to be its own service.

Do the two modes still differ?

Mostly no, and this change makes it clearer. They diverge at SEED ARTIFACT and nowhere else: derivative parses the client's .docx, net-new generates a scaffold. Planning, fan-out, validation, retry, apply, render and delivery are shared.

So why keep two runners?

Not structure — authority. A derivative run may not write; a net-new run must. A client sending a form for validation wants to be told it is wrong, not handed a silently corrected version. Locked regions are the enforcement; separate runners keep that enforcement meaningful.

How the manifest becomes requirements

Req 5 calls this "a simple parsing / normalisation step". The fleet fixture shows it is not simple, and it is worth being concrete — this stage is the highest-risk artefact in the system, because every downstream verdict is graded against its output.

The client's manifest, verbatim:

16 zdjęć,
Pod maską
4x fotele i 2 przekatne pojazdu
2x podsufitka,
Pod maską,
Przednia szyba że środka i zewnątrz
Bieżnik opony
zdjęcie bagażnika + wyposażenia pod klapą
i zegary
Podsufitka trzeba spomiędzy forteli zrobić

Ten lines, and every one of the four hard cases below is in there.

Stage 1 — deterministic pre-split, no model

Break on line boundaries and list markers into candidate chunks. Cheap, reproducible, and it fixes the character offsets provenance depends on. It cannot finish the job.

Stage 2 — extraction pass, small model call

One line, two requirements. Przednia szyba że środka i zewnątrz is a single line naming two separately checkable things — windscreen from inside (R-05) and outside (R-06). Same for bagażnika + wyposażenia pod klapą → R-08, R-09. A line-per-requirement parser silently under-counts.

Counts are not repetitions. 4x fotele is one requirement with expected_count: 4, not four requirements — otherwise you get four near-identical review comments.

A constraint stranded from its subject. Line 10, Podsufitka trzeba spomiędzy forteli zrobić, qualifies 2x podsufitka on line 4 — six lines away. Attach it to the wrong requirement and the wrong photo is rejected; drop it and R-04 passes when it should fail. This is the case that makes a pure line split insufficient, and the reason there is a model here at all.

Genuine ambiguity, surfaced rather than guessed. Pod maską appears twice. One reading gives 15 photos, the other 16 — and the client wrote 16 on line 1. The parser records the ambiguity on the requirement instead of silently picking, and the client sees the resolution in the confirmation reply.

The input is also misspelled throughout — że for ze, forteli for foteli. Normalising before parsing is the obvious move, and it is forbidden, because of the next stage.

Stage 3 — provenance binding

Every Requirement carries a source_span that is a verbatim substring of the raw manifest, asserted as an invariant rather than scored. That is what makes the parse auditable: the client can see exactly which of their own words produced each requirement, typos and all.

Recall ≥ 0.95, precision 1.0

The asymmetry is deliberate. Missing a requirement is recoverable — the client sees the list and says so. Inventing one means telling the client their document fails a rule they never wrote. The verbatim-span check is what catches a parser that has started generating instead of extracting.

Stage 4 — slicing

Requirements are grouped by scope into the slices each agent run owns (req 11). The fixture yields exterior_mechanical, interior, glass, tyres, boot.

Slice boundaries are a real design decision, not bookkeeping: an agent only ever sees its own slice, so two requirements that contradict each other land in different runs and neither notices. That is concern D3 — and slicing is where it is created.

Citations, edits, and structure

Citations must quote, not point

A reference like manifest.txt → R-04 tells the client nothing. They did not write R-04; they wrote 2x podsufitka. A justification is auditable only if it carries the words that actually drove the decision.

Three assertions, all enforced by the fixture: every quote is a literal substring of the manifest — a citation the client cannot find in their own words is worse than none, because it looks like evidence and isn't; the cited line number is where the quote really appears; and every required span is present, not just one.

ReqMust citeWhy both
R-0116 zdjęć + Pod maskąThe repeated line is why two are expected; the client's stated total of 16 is why that reading wins
R-042x podsufitka + Podsufitka trzeba spomiędzy forteli zrobićCite only the first and the client cannot see why two supplied photos failed

Cite one span where two were needed and the comment becomes unanswerable. Dropping R-04's constraint citation, paraphrasing it rather than quoting, or citing it against the wrong line all fail the fixture.

In net-new, everything arrives as an edit

Req 14 says edits are line-targeted with no full regeneration. That constrains net-new more than it first appears: the scaffold generator does not get to emit finished content.

It emits structure only — headings, field labels, empty content slots — declaring its regions as it goes: structure locked, slots editable. Every piece of actual content then arrives through the same Edit(line_id, new_text, requirement_id) path derivative uses.

  • Provenance is total. Artifact.edits becomes the complete account of how the document came to exist. Req 10 asks net-new comments to show how each requirement was realised — this is what makes that answerable rather than asserted.
  • One apply path. APPLY_EDITS is identical in both modes, so locked-region enforcement is exercised by both and cannot rot in the mode that "doesn't need it".
  • The invariant is checkable: every character outside the generated scaffold must be attributable to an Edit carrying a requirement_id. Content with no edit behind it is a bug, however well it reads.

Service structure

Nine agents in parallel will each invent a layout unless one is written down. Both services use the same shape:

services/<name>/src/<pkg>/
  main.py           # app factory + lifespan; nothing else
  api/
    routers/        # thin HTTP layer, one module per resource
    deps.py         # Depends providers — settings, repos, clients
    schemas.py      # HTTP shapes, NOT the wire contracts
  services/         # business logic
  <domain>/         # machine/, agents/, llm/, store/, transport/
The load-bearing rule

services/ must not import fastapi — enforced by import-linter, not review. That is what lets the state machine be driven from a test, the eval harness or a CLI with no HTTP anywhere, and it is why the entire Tier-A suite runs without starting a server.

Three more: routers hold no business logic (a router containing a domain if is in the wrong file); dependencies arrive through Depends, never module-level singletons, so tests can inject the in-memory repository and the fake transport; and mff-contracts is the wire contract while api/schemas.py is HTTP-only — leak one into the other and the frozen package stops being frozen in practice.

State & persistence

Req 12 says the artifact lives "outside any single agent run". In-process that is a Python object — but across an HTTP boundary, a retry, a crash, or a second replica, an in-process object is simply gone. It needs a store, and that store is also what finally gives D2 — job status after confirmation — something to report.

So yes: a Firestore-backed store with async save and load. But it goes behind an interface, not into the flows.

# mff-contracts — frozen alongside the models
class ArtifactRepository(Protocol):
    async def save(self, artifact: Artifact, *, expected_version: int) -> int: ...
    async def load(self, job_id: str) -> tuple[Artifact, int]: ...

class JobRepository(Protocol):
    async def put(self, record: JobRecord) -> None: ...
    async def get(self, job_id: str) -> JobRecord | None: ...

Two implementations: InMemoryRepository for tests, evals and local dev, and FirestoreRepository for GCP via google.cloud.firestore.AsyncClient, which is natively async. The state machine only ever sees the Protocol.

That indirection is not ceremony. It is what lets CI and the entire Tier-A eval suite run with no GCP credentials and no emulator. Provisioning Firestore belongs to the deployment owner; the client code is ours.

Four things a naive save/load gets wrong

1 · Firestore caps a document at 1 MiB

An Artifact carrying every Line of a 50-page form plus a comment per requirement can approach that, and the .docx bytes blow straight past it. So Firestore holds the JSON state and GCS holds the documents, referenced by path. Get this wrong and it surfaces as a hard write failure on exactly the large documents the product exists to handle.

2 · The job record is not the artifact

JobRecord — status, mode, current slice, attempts used, unverified ids, timestamps — is a separate small document that is cheap to poll. That is the D2 answer, and it stays readable even while the artifact is mid-write.

3 · Optimistic concurrency

The artifact is mutated across many slice runs. Carry a version int and check it on write. v1 runs slices sequentially so it should never fire — but if it ever does, a lost update means silently dropped review comments, which is the worst failure available here, because the output still looks complete.

4 · Checkpoint per slice, not per job

Save after each slice completes. That makes a crashed job resumable rather than restartable, and gives the job record real progress to report instead of a binary running/done.

The blob pointer

Firestore stores the run's shape; the bucket stores its weight. One reference type covers both directions:

class BlobRef(BaseModel):
    uri: str            # gs://<bucket>/jobs/<job_id>/<kind>/<sha256>
    content_type: str
    size_bytes: int
    sha256: str

It carries the client's source .docx, the rendered output, and every image extracted from a form. Content-addressing by sha256 means a retried job re-points at the existing object rather than writing a second copy — which matters, because req 17 retries up to three times and a naive path scheme would triple-write on every recovery.

This is also the seam the deferred image module — B11 — picks up: it reads BlobRefs already sitting on the artifact and returns crops as new ones. No schema change when it lands, which is the whole reason for stubbing the interface now rather than leaving a hole.

The frozen contract

Everything else is written against mff-contracts. No branch may edit it — a change request goes back through the layer-0 owner. This single rule is what makes seven simultaneous PRs safe.

class Requirement(BaseModel):
    id: str                 # "R-03"
    text: str               # one checkable statement (req 5)
    source_span: str        # verbatim manifest text it came from
    scope: str              # slice key — which run owns it (req 11)
    applies_to: list[str]   # form ids; empty = all

class Line(BaseModel):      # the unit edits target (req 14)
    id: str                 # stable: "p12", "t3.r2.c1.p0"
    text: str

class Region(BaseModel):
    line_ids: list[str]
    locked: bool
    rationale: str          # why the first run classified it so

class ReviewComment(BaseModel):
    line_id: str
    requirement_id: str
    verdict: Literal["pass", "fail", "realised", "unverified"]
    justification: str      # req 16: every answer justified
    suggestion: str | None  # required when verdict == "fail"
    citations: list[Citation]  # the client's own words, quoted

class Citation(BaseModel):
    quote: str              # VERBATIM substring of manifest_raw
    line: int               # 1-indexed line it appears on
    start: int; end: int    # manifest_raw[start:end] == quote

class SliceRequest(BaseModel):   # orchestrator → one instance
    slice_id: str
    requirements: list[Requirement]  # this slice only
    artifact: Artifact               # READ-ONLY snapshot
    editable_line_ids: list[str]     # scope bound; else rejected

class SliceReport(BaseModel):    # instance → orchestrator
    slice_id: str; attempt: int
    edits: list[Edit]                # PROPOSED, not applied
    comments: list[ReviewComment]
    unanswered: list[str]

class JobAccepted(BaseModel):  # the 202 — req 7 quotes exactly this
    job_id: str
    requirements: list[Requirement]   # parsed once, here

class Artifact(BaseModel):  # req 12: outlives any single run
    lines: list[Line]
    regions: list[Region]
    edits: list[Edit]
    comments: list[ReviewComment]

Evals & latency budgets

Every branch ships an eval suite. A PR without one does not merge. No subagent gets to claim "it works" on its own recognisance — each stage produces a number.

Two tiers

Tier A — deterministic components. No model anywhere: docmodel, intake rules, transport, contracts, the store. Golden assertions plus a wall-clock budget. Runs in CI on every push.

Tier B — pipeline evals. The system under test calls a live model, so it costs money and runs nightly or on demand rather than on every push. CI substitutes TestModel.

The scorer is structural in both tiers

No LLM-as-judge anywhere. The pipeline is non-deterministic; whether its output is complete is not. A judge is the wrong instrument here — the question is not "is this justification well written" but "does every requirement have a verdict, does every failure carry a suggestion, does every reference resolve, and are the verdicts right". All decidable by reading the document.

Scoring is a violation count against a spec, threshold zero. Deliberately not a text-similarity comparison against the golden output either: that fails on a harmlessly reworded justification while passing a document with the wrong verdicts.

Invariants are not scores

Some things are contract violations, not quality signals, and are asserted at 1.0 with no tolerance: every requirement answered; every answer justified; every source_reference resolving; every fail carrying a suggestion; no edit ever landing in a locked region.

Everything else is scored against a threshold. Blurring the two is how eval suites go green while the product is broken.

Mutation-test the evaluator

An evaluator that has only ever seen correct output is worthless — it may be asserting nothing. Every branch must break its own golden output in at least three ways and show the evaluator catching each.

This is not a hypothetical discipline. The fleet fixture's reference checker had a real bug — a field extractor that swallowed the rest of the comment, so a one-character justification still passed a length check — and only mutation testing found it. Five deliberate regressions now run against it; all five are caught, and the golden output still passes 88 of 88.

Code quality bar

Seven agents writing in parallel is exactly how a codebase turns to mud. The defence has to be machine-enforced, not review-enforced — no human reliably catches architectural drift across a dozen concurrent PRs.

Enforced in CI

  • ruff lint and format, one shared config, zero per-package overrides.
  • mypy --strict across the workspace. A type: ignore needs a specific error code and a reason.
  • import-linter pinning dependency direction: services → packages → contracts. Never sideways, never upward. This is the highest-value gate here — it is what stops B6 reaching into B4's internals at 2am.
  • No model call outside llm/ and agents/, enforced by the same contracts.
  • Per-package coverage ≥ 85%, measured per package. A global number lets one well-tested package hide four untested ones.

Conventions

  • Prompts live in versioned files under agents/<name>/prompts/, never inline f-strings. They are the highest-churn, highest-impact artefact in the repo and they need a diff history.
  • Each package declares its public API via __all__; everything else is private and may change without notice.
  • Structured logging only, with job_id and slice bound on every line. Print statements fail lint.
  • Any decision worth arguing about gets an ADR. Cheap to write, and it stops the same debate recurring across three PRs.
  • Domain language matches the spec exactly — Requirement, Artifact, Line, Region, slice, verdict. No synonyms.

Subagent brief

Each Sonnet agent receives, verbatim:

  • The requirement ids from the PDF it must satisfy — B1 owns reqs 14 and 15; B5 owns 11, 12, 16, 17.
  • The exact directories it owns, and that touching anything else — mff-contracts above all — is out of bounds. Raise it in the PR description instead.
  • The frozen contract signatures it consumes and produces.
  • Test requirements: unit tests in its own package, no live model calls in CI, make check green.
  • Eval requirements: the evals/ directory for its stage, invariants asserted at 1.0, and the recorded baseline pasted into the PR description. A branch that cannot state its numbers is not done.

Verification

  • make check — ruff, mypy, import-linter, pytest across the workspace, no network.
  • Round-trip a fixture docx; assert line ids stable and a locked-region edit raises; open the output in Word and confirm comments land in the review pane.
